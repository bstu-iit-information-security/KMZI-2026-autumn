                         (сбор ошибок в маску без early exit)

Язык ................... C++17
BigInt-библиотека ...... GMP (только арифметика больших чисел)
SHA-256, MGF1, OAEP, RSA, CRT, Миллер-Рабин, расширенный Евклид,
модульное возведение в степень написаны вручную.

3. СТРУКТУРА ПРОЕКТА И СООТВЕТСТВИЕ МЕТОДИЧКЕ
======================================================================
Три логически изолированных модуля, как требует методичка:

МОДУЛЬ 1. Теория чисел и арифметика RSA  (rsa_math.hpp / rsa_math.cpp)
    ext_gcd        расширенный алгоритм Евклида
    gcd, lcm       НОД и НОК (lcm нужен для функции Кармайкла)
    mod_inverse    обратный элемент через ext_gcd
    mod_pow        модульное возведение в степень (square-and-multiply)
    is_probable_prime  тест Миллера-Рабина (40 раундов) + пробное деление
    generate_prime     простое число заданной длины (2 старших бита = 1,
                       чтобы N гарантированно имел ровно 2048 бит)
    generate_keypair   генерация ключей, предвычисление dp, dq, qinv
    Ключи: Public (N, e), Private (N, d, p, q, dp, dq, qinv).
    e = 65537, lambda(N) = lcm(p-1, q-1), d = e^-1 mod lambda(N).
    p > q гарантируется (нужно для корректной работы алгоритма Гарнера).

МОДУЛЬ 2. Вычислительное ядро RSA с CRT  (rsa_core.hpp / rsa_core.cpp)
    rsa_encrypt_raw     c = m^e mod N
    rsa_decrypt_plain   m = c^d mod N (для сравнения скорости)
    rsa_decrypt_crt     расшифрование по алгоритму Гарнера (боевое)
    rsa_encrypt_block / rsa_decrypt_block  преобразование байты <-> число
                        фиксированной длины k = 256 байт

МОДУЛЬ 3. OAEP и Constant-Time защита  (oaep.hpp / oaep.cpp)
    oaep_pad      упаковка (PKCS#1 v2.1): lHash || PS || 0x01 || M,
                  MGF1, маскирование seed и DB
    oaep_unpad    constant-time распаковка (ЗАДАЧА ВАРИАНТА 1)
    oaep_encrypt / oaep_decrypt   OAEP + RSA целиком

Вспомогательные файлы:
    bigint.hpp/.cpp  RAII-обёртка над GMP mpz_t (вся работа с GMP тут)
    sha256.hpp/.cpp  собственная реализация SHA-256
    ct.hpp           constant-time примитивы (маски вместо if)
    rng.hpp/.cpp     источник случайности (/dev/urandom)
    main.cpp         тесты и измерения
    Makefile         сборка

4.1 Математическая часть: ускорение через CRT
---------------------------------------------
Стоимость возведения в степень n-битного числа по n-битному модулю
~ n^3 (n шагов, на каждом умножение за n^2).

Обычное расшифрование: одна экспонента 2048 бит по модулю 2048 бит
    стоимость ~ 2048^3 = 8 * 1024^3.

CRT: две экспоненты по 1024 бит по модулям 1024 бит
    стоимость ~ 2 * 1024^3.

Отношение: (8 * 1024^3) / (2 * 1024^3) = 4  -> ускорение до 4 раз.
На практике с GMP получилось ~3 раза (ускорение не идеальное из-за
накладных расходов на деление и т.п.). В тесте: plain 5.2 мс, CRT 1.7 мс.

Алгоритм Гарнера:
    m1 = c^dp mod p
    m2 = c^dq mod q
    h  = qinv * (m1 - m2) mod p     (если m1 - m2 < 0, добавить p)
    m  = m2 + h * q

Почему работает: m = m2 + h*q удовлетворяет m = m2 (mod q) и
m = m2 + qinv*(m1-m2)*q = m2 + (m1-m2) = m1 (mod p), потому что
qinv*q = 1 (mod p). По китайской теореме об остатках решение
единственно по модулю N = p*q.

Демонстрация на малых числах (она печатается программой):
    p=61, q=53, N=3233, lambda=780, e=17, d=413
    dp = 413 mod 60 = 53
    dq = 413 mod 52 = 49
    qinv = 53^-1 mod 61 = 38
    m = 65, c = 65^17 mod 3233 = 2790
    m1 = 2790^53 mod 61 = 4
    m2 = 2790^49 mod 53 = 12
    (m1 - m2) = -8 < 0  -> +61 = 53
    h = 38 * 53 mod 61 = 1
    m = 12 + 1 * 53 = 65   <- исходное сообщение

Про "добавить p": это работает, потому что p > q, значит m2 < q < p
и разность m1 - m2 > -p. Поэтому в генерации ключей стоит swap p и q.

4.2 Архитектурная схема (поток данных)
--------------------------------------
Шифрование:
    сообщение M (0..190 байт)
      -> oaep_pad: lHash = SHA256(label)
                   PS = нули длины 190 - len(M)
                   DB = lHash || PS || 0x01 || M        (223 байта)
                   seed = random (32 байта)
                   dbMask = MGF1(seed, 223); maskedDB = DB xor dbMask
                   seedMask = MGF1(maskedDB, 32); maskedSeed = seed xor seedMask
                   EM = 0x00 || maskedSeed || maskedDB   (256 байт)
      -> байты в число m (m < N, т.к. первый байт 0x00)
      -> c = m^e mod N
      -> шифротекст 256 байт

Расшифрование:
    шифротекст 256 байт
      -> число c, проверка c < N
      -> m = Garner(c)  (CRT)
      -> EM 256 байт фиксированной длины
      -> oaep_unpad (constant-time): снять маски, проверить всё,
         извлечь сообщение по маске
      -> OaepResult { ok, len, msg[190] }

4.3 Анализ безопасности (Constant-time, задача варианта 1)
----------------------------------------------------------
Атака: Блейхенбахера/Мангера. Если функция распаковки выходит с ошибкой
сразу после первой найденной проблемы (early exit), то по времени работы
атакующий понимает, какая именно проверка не прошла, и по этой информации
восстанавливает открытый текст.

Как это устранено в oaep_unpad:
  1. Нет ни одного return/break/continue внутри обработки секретных данных.
     Функция имеет единственную точку выхода в конце.
  2. Все проверки выполняются ВСЕГДА до конца:
       - байт em[0] должен быть 0
       - lHash из DB сравнивается с вычисленным (все 32 байта)
       - поиск разделителя 0x01 идёт по ВСЕМ 191 байтам PS-области
  3. Ошибки копятся в аккумуляторе err (битовая маска):
       err  = em[0]
       err |= db[i] ^ lhash[i]          (для всех i)
       err |= looking & ~is_null        (байт не 0x00 и не 0x01 до разделителя)
       err |= looking                   (разделитель не найден)
     valid = ct_is_zero(err)  -> 0xFFFFFFFF, только если ошибок не было
  4. Позиция разделителя ищется без if: переменная looking (маска) гасится
     при встрече первого 0x01, index обновляется через ct_select.
  5. Сообщение извлекается без ветвлений: двойной цикл по фиксированным
     границам (190 x 223). Для каждого выходного байта j собирается
     db[i] & (i == start+j) по всем i, затем маскируется in_range и valid.
     Индексы массивов - только счётчики циклов (публичные), а не секреты,
     поэтому нет и cache-timing зависимости от секретного индекса.
  6. При ошибке выдача обнуляется маской (msg = 0, len = 0, ok = 0).
     Наружу не сообщается, какая именно проверка не прошла.
  7. Единственные ветвления зависят от ПУБЛИЧНЫХ данных: длина шифротекста
     и условие c < N (это проверяется открыто и по стандарту).

Примитивы в ct.hpp: ct_is_zero, ct_eq, ct_lt, ct_select - только
побитовая арифметика, без if и без тернарных операторов.

Память: все буферы - массивы фиксированного размера на стеке
(uint8_t db[223], seed[32], em[256] и т.д.). Никаких vector<vector<>>,
никаких динамических вложенных контейнеров в OAEP-модуле.
Секретные буферы затираются через secure_zero (volatile).

Что сказать про оговорку: компилятор теоретически может превратить
маски в ветвления, поэтому в работе это проверено ИЗМЕРЕНИЕМ тактов
(п. 4.4), а не только чтением кода.

6. ВОЗМОЖНЫЕ ВОПРОСЫ НА ЗАЩИТЕ И ОТВЕТЫ
======================================================================
В: Почему нельзя Python?
О: Методичка запрещает языки с автоматическим расширением памяти под
   переменные: нет контроля над размещением и затиранием секретов.

В: Что такое OAEP и зачем он нужен?
О: "Сырой" RSA детерминирован: один M -> один C, уязвим к CCA и подбору.
   OAEP добавляет случайный seed и маскирует данные через MGF1, делая
   шифрование вероятностным и защищая структуру сообщения.

В: Что делает MGF1?
О: Из строки Z и длины L строит маску: конкатенирует
   SHA256(Z || счётчик_4_байта) для счётчика 0,1,2,... пока не наберётся L
   байт, затем обрезает.

В: Почему первый байт EM равен 0x00?
О: Чтобы число m гарантированно было меньше N (N имеет старший бит 1,
   значит любое число с нулевым старшим байтом меньше N).

В: Почему длина сообщения не более k - 2*hLen - 2?
О: В EM размером k байт: 1 байт 0x00, hLen байт seed, hLen байт lHash,
   минимум 1 байт разделителя 0x01 -> остаётся k - 2*hLen - 2.

В: Что такое функция Кармайкла и чем она лучше Эйлера?
О: lambda(N) = lcm(p-1, q-1) - наименьший показатель, для которого
   a^lambda = 1 mod N. Она делит phi(N), поэтому d получается меньше,
   при этом расшифрование работает так же.

В: Зачем тест Миллера-Рабина, почему не просто деление?
О: Пробное деление для 1024-битных чисел нереально по времени.
   Миллер-Рабин вероятностный: вероятность ошибки для составного числа
   не больше 4^-раундов, у нас 40 раундов (< 2^-80).

В: Почему p > q?
О: Чтобы m2 < q < p, тогда m1 - m2 > -p, и добавления одного p хватает,
   как сказано в методичке.

В: Как атака Блейхенбахера связана с задачей?
О: Если сервер различает ошибки (по ответу или по времени), атакующий
   подбирает шифротексты и получает оракул "корректен ли формат EM".
   Для OAEP (атака Мангера) оракул даёт информацию о первом байте. Мы
   убираем различие во времени и возвращаем единый статус ok = 0.

В: Как вы доказываете отсутствие зависимости от секрета?
О: Двумя способами. Статически: нет return/if/тернарных операторов,
   зависящих от секретных данных, циклы с фиксированными границами,
   доступ к массивам по счётчикам циклов. Эмпирически: измерение тактов
   на шести классах входов даёт отклонение медиан около 0.03%.

В: Где у вас динамическая память?
О: В OAEP-модуле нет совсем: массивы фиксированного размера на стеке.
   Динамика (BigInt от GMP) есть только в арифметике больших чисел,
   что разрешено методичкой.

В: Что делает ct_select(mask, a, b)?
О: Возвращает a, если mask = 0xFFFFFFFF, и b, если mask = 0:
   (a & mask) | (b & ~mask). Это замена if без ветвления.

В: Почему сравнение lHash сделано через ИЛИ от XOR?
О: Если все байты равны, XOR даёт нули, их OR = 0. Любое различие
   даёт ненулевой бит, который остаётся в аккумуляторе. Сравниваются
   все 32 байта, без раннего выхода (как memcmp).

В: Ваш mod_pow constant-time?
О: Нет, и по варианту 1 это не требуется (это задачи вариантов 2, 8).
   В варианте 1 constant-time относится к деинкапсуляции OAEP.
   Можно добавить, что для защиты mod_pow нужна лестница Монтгомери
   или слепота RSA (варианты 2, 4).
